 Dual-core split: pin flight-control loop to core 1, comms to core 0

 Context

 ESP-Drone runs on ESP32-S3 (dual-core), and CONFIG_FREERTOS_NUMBER_OF_CORES=2 / CONFIG_FREERTOS_UNICORE
 is already off for this target (sdkconfig.defaults.esp32s3). However, no task in the codebase is pinned
 to a core — every xTaskCreate/xTaskCreateStatic call (grepped across the repo) passes no affinity, so the
 FreeRTOS SMP scheduler is free to bounce any task, including the sensor/estimator/control loop, onto
 either core alongside Wi-Fi/UDP traffic. app_main() itself is pinned to core 0
 (CONFIG_ESP_MAIN_TASK_AFFINITY_CPU0=y), so systemTask and everything it spawns today land unpinned, with
 no real isolation between flight control and comms.

 Goal: give the flight-critical sensor-fusion + control pipeline (sensors → Kalman estimator → stabilizer,
 plus the optional deck-sensor feeders) exclusive use of core 1, and pin the Wi-Fi/CRTP communication
 tasks to core 0 (where app_main/systemTask already live), so the two genuinely run in parallel instead of
 time-sharing one core. Single-core targets (ESP32-S2, CONFIG_FREERTOS_UNICORE=y) must keep working
 unaffected — fall back to tskNO_AFFINITY there, mirroring the existing #if CONFIG_FREERTOS_UNICORE
 precedent already used for KALMAN_TASK_PRI in components/config/include/config.h:118.

 Changes

 1. components/config/include/config.h — new core-affinity macros

 Add right after the task-priority block (after line 121, the existing CONFIG_FREERTOS_UNICORE
 KALMAN_TASK_PRI override):

 // Core affinity: dedicate core 1 to the flight-critical sensor -> estimator
 // -> stabilizer pipeline, and keep comms (Wi-Fi/CRTP) on core 0, where
 // app_main/systemTask already run (CONFIG_ESP_MAIN_TASK_AFFINITY_CPU0).
 // Single-core targets have no second core to dedicate.
 #if CONFIG_FREERTOS_UNICORE
   #define FLIGHT_CTRL_TASK_CORE tskNO_AFFINITY
   #define COMM_TASK_CORE        tskNO_AFFINITY
 #else
   #define FLIGHT_CTRL_TASK_CORE 1
   #define COMM_TASK_CORE        0
 #endif
 (tskNO_AFFINITY comes from task.h, already included by every file that uses these macros.)

 2. components/core/crazyflie/modules/interface/static_mem.h — pinned variant of the static-task macro

 Most flight/comm tasks are created via STATIC_MEM_TASK_CREATE(...) (→ xTaskCreateStatic, no core param).
 Add a sibling macro rather than changing the existing one (avoids touching ~15 unrelated call sites):

 /**
  * @brief Create a task pinned to a specific core, using static memory.
  * Same as STATIC_MEM_TASK_CREATE() but binds the task to CORE_ID.
  */
 #define STATIC_MEM_TASK_CREATE_PINNED(NAME, FUNCTION, TASK_NAME, PARAMETERS, PRIORITY, CORE_ID) \
   xTaskCreateStaticPinnedToCore((FUNCTION), (TASK_NAME), osSys_ ## NAME ## StackDepth, (PARAMETERS),
 (PRIORITY), osSys_ ## NAME ## StackBuffer, &osSys_ ## NAME ## TaskBuffer, (CORE_ID))

     Out of scope

     Low-rate/system tasks (systemTask, logTask, paramTask, memTask, infoTask, pmTask, ledseq, legacy
     syslink/uart2/usblink/extrx) stay unpinned — they're priority 1-2, infrequent, and pinning them adds
     diff churn without meaningfully affecting the flight-loop/comms isolation this task is about.
     app_main's own affinity is already fixed by CONFIG_ESP_MAIN_TASK_AFFINITY_CPU0 (untouched).
