 Dual-core split: pin flight-control loop to core 1, comms to core 0

 Context

 ESP-Drone runs on ESP32-S3 (dual-core), and CONFIG_FREERTOS_NUMBER_OF_CORES=2 / CONFIG_FREERTOS_UNICORE
 is already off for this target (sdkconfig.defaults.esp32s3). However, no task in the codebase is pinned
 to a core — every xTaskCreate/xTaskCreateStatic call (grepped across the repo) passes no affinity, so the
 FreeRTOS SMP scheduler is free to bounce any task, including the sensor/estimator/control loop, onto
 either core alongside Wi-Fi/UDP traffic. app_main() itself is pinned to core 0
 (CONFIG_ESP_MAIN_TASK_AFFINITY_CPU0=y), so systemTask and everything it spawns today land unpinned, with
 no real isolation between flight control and comms.

 Goal: give the flight-critical sensor-fusion + control pipeline (sensors → Kalman estimator → stabilizer,
 plus the optional deck-sensor feeders) exclusive use of core 1, and pin the Wi-Fi/CRTP communication
 tasks to core 0 (where app_main/systemTask already live), so the two genuinely run in parallel instead of
 time-sharing one core. Single-core targets (ESP32-S2, CONFIG_FREERTOS_UNICORE=y) must keep working
 unaffected — fall back to tskNO_AFFINITY there, mirroring the existing #if CONFIG_FREERTOS_UNICORE
 precedent already used for KALMAN_TASK_PRI in components/config/include/config.h:118.

  2. 抬头/低头没有严格按 m1m4/m2m3 对称规律走

  看混控公式的全貌（power_distribution_stock.c:98-101）：

  m1 = thrust - r + p + yaw
  m2 = thrust - r - p - yaw
  m3 = thrust + r - p + yaw
  m4 = thrust + r + p - yaw

  脚本注释只强调了 p（pitch）这一项，但实际每个电机同时叠加了 r(roll/2) 和 yaw 两项。破坏对称性的来源：

  - 手动倾斜天然带耦合：人手很难做到纯 pitch、零 roll、零 yaw。roll 项让 m1,m2 同号变化、m3,m4
    同号变化；这和 pitch 项的 m1,m4 同号 / m2,m3 同号是两条不同的配对关系，叠加后单纯看"m1m4 vs
    m2m3"这条规律会被 roll/yaw 分量的抖动掩盖。
  - 未滤波 D 项叠加高频噪声：同第1点，逐帧打印出来的数字不是干净的准静态 pitch-P 响应，而是"低频 pitch 趋势
    + 高频 D 项抖动"的混合，肉眼看会觉得"没有完全跟着规律走"。
  - idleThrust=0 造成的非对称钳位：基线只有 15000，一旦某个电机侧的修正量把它顶到 0
    地板，它就不能再跟着倾角继续线性下降了——比如低头时 m2 已经被钳到 0，继续加大低头角度，理论上 m2
    该继续减小，但地板效应让它纹丝不动，只有 m3 在涨，破坏了"一个减一个增"的对称直觉。
  - 串级 PID 的动态滞后/超调：姿态是外环 P（角度）→ 内环 PID（角速度）的串级结构，手动快速倾斜时会有瞬态超

  PID 算法：并联式(非交互型)离散 PID，微分对误差、矩形积分、积分限幅无输出限幅

  pid.c:56-102 的 pidUpdate 是教科书式并联形式（P、I、D 三项独立增益相加，不是"单一 Kp 乘以 I/D 相对项"的
  ideal/standard form）：

  - P：outP = kp * error，error = desired - measured（pid.c:62，误差对测量值/角度求差，标准负反馈）。
  - D：deriv = (error - prevError) /
    dt（pid.c:68）——这是微分对误差(derivative-on-error)，不是更常见的"微分对测量值(derivative-on-measuremen
    t)"写法。区别在于：如果期望值(desired)有台阶跳变，这种写法会产生"微分冲击(derivative kick)"；本项目里
    desired 是姿态环输出的连续 rateDesired，跳变不算典型阶跃，但对噪声/尖峰同样敏感（见上一条分析）。
  - I：integ += error * dt（pid.c:81），矩形/欧拉积分，然后 constrain(integ, -iLimit, iLimit)
    做积分幅值限幅式抗饱和（pid.c:84-87）——这是最基础的一种抗积分饱和手段(clamped
    integrator)，不是条件积分(conditional integration)或反算法(back-calculation)，也就是说输出真正打满饱和
    时积分项不会自动停止累积，只是被限制在一个固定上限内。
  - 总输出限幅：if (outputLimit != 0) constrain(...)（pid.c:93-96），而角度/角速度环用的默认值
    DEFAULT_PID_OUTPUT_LIMIT=0.0（pid.h:66/100），按代码里 !=0
    才生效的写法，等于没有限幅——这也是上一条分析里电机尖峰的另一个成因。

  结构上是串级(cascade) 姿态控制：外环角度 P（attitudeControllerCorrectAttitudePID，只用了 pidRoll/pidPitch
  的 pidUpdate，但这几个 PID 对象在 pidInit 时 PID_ROLL_KI/KD 等增益，具体是不是纯 P 取决于 pid.h
  里的宏值）→ 内环角速度 PID（attitudeControllerCorrectRatePID，pidRollRate/pidPitchRate/pidYawRate 是完整
  PID）。这和 PX4/Crazyflie 生态里经典的"angle-P + rate-PID"级联架构是一致的。

  一句话总结：滤波算法是二阶 Butterworth biquad，但默认关闭；PID 是最朴素的并联式离散 PID（微分对误差 +
  矩形积分 + 积分限幅 + 默认不限幅输出），没有任何现代变体（如微分对测量值、反算法抗饱和、前馈等）。这两点
  合起来正好解释了你之前问的"电机起转尖峰"和"pitch 响应不干净"的问题根源。

● 为什么 Kalman 会周期性归零——精确到公式

  kalman_core.c 里飞机"未起飞"（quadIsFlying==false）时的预测模型是这样算速度的（约化写法）：

  S[PX] += dt * (acc.x - GRAVITY_MAGNITUDE * R[2][0])

  这一步的意图是：假设飞机静止，加速度计读数应该只剩重力分量，用当前姿态估计 R
  算出"理论上应该测到多少重力分量"，减掉之后剩下的残差当作真实运动加速度积分成速度。

  问题就在这里：姿态四元数在"未起飞"这条路径下完全靠陀螺仪积分推进，没有任何环节用加速度计去反过来修正它。
  你把机身固定倾斜 θ 角不动，R 一直停在（或缓慢漂离）水平附近，但加速度计測到的其实是真实的 g·sin(θ)
  这部分重力分量——这部分不是运动，但因为 R
  没跟着倾斜更新，程序把它当成"残差"整个积分进了速度状态，速度会以近似 g·sin(θ) 的恒定加速度线性增长。

  代入数字对一下：θ≈30° 时，g·sin(30°) ≈ 4.9 m/s²，速度到 kalman_supervisor.c 里 maxVelocity=10 m/s
  的边界要花：
  t = 10 / 4.9 ≈ 2.04 秒
  跟你实测的周期（325805→327805，正好2.000秒）几乎完全吻合。这不是巧合，是这条"未起飞时直接把加速度计残差积
  分进速度、且没有姿态修正"的预测模型在数学上必然产生的结果。一旦速度越界，kalman_supervisor.c
  判定状态越界，整个估计器 resetEstimation，姿态四元数被强制拉回水平（对应你看到的 pitch
  瞬间归零），然后重新开始漂，循环往复。

  这套设计是照搬 Bitcraze Crazyflie 的思路：假设起飞前机身基本水平、起飞后很快进入"飞行中"分支（这条分支的
  物理模型不同，而且实际飞行时姿态误差通常很小、时间尺度短，不会攒到这么大的速度误差）。它本质上没考虑"长时
  间静止但大角度倾斜"这种台架测试场景——正常飞行中不太会出现这个问题，除非真的炸机躺在地上倾斜很久。

  怎么兼顾光流+ToF 又不掉进这个坑

  互补滤波器确实不做位置/速度融合，用不了 PMW3901/VL53 的数据——所以不能一刀切全用
  complementary。比较合理的做法是按场景切换估计器，而不是二选一定死：

  - 台架/地面诊断测试（t4_imu_axis_check.py、t4b_pitch_response_check.py
    这类：飞机固定不动、不真正起飞、也用不上光流/ToF数据）→ 用
    complementary，就是现在这个改法，不会有周期归零问题。
  - 真实飞行/悬停测试（会起飞、需要 POSHOLD_MODE 靠光流+ToF定点）→ 让固件按原设计自动切
    Kalman（也就是别在这些飞行测试脚本里调 ensure_complementary_estimator）。正常飞行时 PID
    会把姿态维持在小角度附近，不会出现"倾斜30°+静止2秒不动"这种持续误差累积的极端情况，Kalman
    的这个边界情况基本不会被触发。

  所以我建议：保留刚才在 t4_imu_axis_check.py/以后的地面台架脚本里做的估计器强制切换，但不要在真正试飞/定点
  悬停用的代码或脚本里做这个切换——光流+ToF该用的时候还是让 Kalman
  正常工作,只是别在"夹住不让转"的台架测试场景下用它。

  如果你确实需要 Kalman 在被夹住静止倾斜的情况下也不发生这个问题（比如做长时间地面调试还想看 Kalman
  融合效果），那就得动固件本身：给"未起飞"这条预测路径加一个基于加速度计的姿态修正（本质上是给 Kalman

找到真正的根因了，而且比之前想的更严重——不是估计器的问题，是 commander 的飞行模式没切回来。

  根因

  setCommandermode(POSHOLD_MODE) 除了强制锁定 Kalman 估计器，还同时打开了两个开关：altHoldMode=true 和
  posHoldMode=true（crtp_commander_rpyt.c:100-104）。之前我们只把估计器切回了
  complementary，没动这两个开关，它们是独立的模块静态变量，跟估计器无关。

  altHoldMode=true 时，RPYT 解码器（crtp_commander_rpyt.c:182-189）会直接丢弃脚本发的原始 thrust
  值，把它重新解释成一个 Z 轴速度目标，交给定高/速度 PID 处理，这个 PID 有一个固定的前馈量 thrustBase=36000
  （满量程65535的一大半），P项还没有上限（position_controller_pid.c:216-244）——前馈+P项加起来在一个 10ms
  的位置控制周期内就能冲到
  68767，早就超过65535了。这比脚本"1秒斜坡爬升"快了100倍，完全解释了为什么只过50ms电机就直接顶满。

  posHoldMode=true 还会把 roll/pitch 也交给速度PID（pidVX/pidVY）而不是脚本发的
  0/0——飞机静止时估计出的微小速度噪声就会被当成"需要纠正的速度"，直接转成 roll/pitch
  姿态指令，这解释了为什么是"3个电机打满、1个电机没动"这种不对称模式，而不是4个一起打满。

  修复

  固件把这两个开关也做成了可写参数（flightmode.althold、flightmode.poshold），不用重新编译，跟切估计器一样
  的套路。我把它加到 t4b_pitch_response_check.py 里。
