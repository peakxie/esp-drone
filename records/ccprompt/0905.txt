  各自的分量（也就是这个倾角矢量指向哪个方向）随着 yaw 在转。这是一个很典型的信号：

  - 如果是机身/IMU 本身固定装歪了（body-frame 固定偏置），那这个偏置是焊在机身上的，不管你怎么转
    yaw，它在机体坐标系里应该是个固定值——roll、pitch 各自应该稳定在差不多的数上，不会随 yaw 转方向。

  3. PMW3901 光流是从多高开始参与"偏移控制"的？

  结论：没有任何"高度低于多少就不用光流"的开关，光流数据从贴地一直到失效距离上限，理论上一直在被使用。具体
  看代码：

  - flowdeck_v1v2.c 里，只要 motion.motion==0xB0（有效帧）且像素位移没超过 outlier
    阈值（OULIER_LIMIT=100），就直接 estimatorEnqueueFlow() 塞进 EKF 队列——完全没有检查 range.zrange
    或高度。
  - 真正跟高度有关的地方在 EKF 内部：kalman_core.c 的 kalmanCoreUpdateWithFlow()，用当前估计的高度（KC_STAT
    E_Z，不是测距原始值）作为光流像素位移换算成速度/位置的比例因子分母（z_g），但这个 z_g 被下限钳位在
    0.1m：

  if (this->S[KC_STATE_Z] < 0.1f) { z_g = 0.1; } else { z_g = this->S[KC_STATE_Z]; }

  关键点：t5 的 LIFTOFF_HEIGHT_M=0.03m，起飞最初这一段真实/估计高度是明显低于 0.1m 的，但换算光流用的 z_g
  会被强行按 0.1m 算（比真实高度高出 3 倍以上）。这个换算关系是 速度 ∝
  1/z_g，也就是这段时间无论真实高度多低，EKF 都按"假设你在 0.1m
  高"去解读光流像素位移——这跟你实际高度差得越远，换算出来的水平速度误差就越大。

  这其实也补上了之前"漂移在爬升阶段增长得比悬停阶段更快"这个现象的一个具体机制解释：不只是姿态偏置，起飞头
  几十厘米这段时间光流本身的比例因子就是错的（被钳在 0.1m 下限），越贴地误差越大。

  2. 能不能靠调控制参数把偏移压住？

  代码里（position_controller_pid.c）水平方向其实已经是两层 PI 控制器，不是纯 P：

  - 内层速度环 pidVX/pidVY：kp=25, ki=1.0, kd=0
  - 外层位置环 pidX/pidY：kp=1.9, ki=0.1, kd=0（但只有 mode.x/y==modeAbs 时才会跑）

  关键点：t5_hover_land.py 用的 send_hover_setpoint 对应固件里 mode.x=modeVelocity,
  mode.y=modeVelocity（不是 modeAbs）——我刚确认了 crtp_commander_generic.c 里 hover 对应的解码就是设成
  modeVelocity。这意味着现在飞的时候，外层那个真正"盯着绝对位置误差去纠正"的 PI
  环（pidX/pidY）根本没有参与，只有内层速度环在跑，它的目标只是"把速度纠到
  0"，不是"把位置纠回原点"——如果有一个持续存在的偏置（配平残余、或者上面说的低高度光流比例因子误差），速度
  环的积分项理论上能在稳态慢慢把它吃掉、让速度收敛到
  0，但在它吃掉之前累积的那段位置误差是回不来的，这跟你观察到的"匀速甚至加速式漂移"是一致的。

  所以：
  1. 可以调，但这不是最对症的调法——单纯加大 vxKi/vyKi（当前 1.0）能让速度环更快地把恒定偏置纠正到
     0，减少漂移时间，但调太大容易放大噪声、引起振荡，属于"治标"。
  2. 更对症的做法是换成绝对位置模式，也就是用 cflib 里对应 mode.x/y=modeAbs 的 setpoint 接口（比如
     send_position_setpoint），这样会真正启用 pidX/pidY
     那层位置闭环——它直接对"离目标点多远"这个误差做闭环修正，而不是只管速度是不是
     0，理论上能更主动地把飞机"拉回"原地，而不只是"不再继续漂"。
  3. 但不管调哪层参数,前提都是这个偏置本身是个近似恒定、方向不乱变的量——如果偏置本身随高度/姿态变化（比如上
     面提到的光流比例因子误差只在贴地时明显),单靠一组固定 PI
     增益也很难完全兼顾"贴地时误差大、悬停时误差小"这两种情况,还是得先把偏置源头（配平 +
     光流低高度换算误差）压下去,再谈调参数会更有效。
