  1. 定点模式下起飞/悬停/降落的固件流程

  这个项目里的"定点模式"（POSHOLD_MODE）本质是开机自检时的一次性选择，不是飞行中动态切换的。 调用链在
  sensors_mpu6050_hm5883L_ms5611.c 的传感器初始化里：

  sensorsInit()
    → zRanger2Init()/zRanger2Test()      // 测距(VL53L1X)检测
    → flowdeck2Init()/flowdeck2Test()    // 光流(PMW3901)检测
         检测成功 → setCommandermode(POSHOLD_MODE)
                      → altHoldMode=true; posHoldMode=true
                      → registerRequiredEstimator(kalmanEstimator)
         只有气压计、没光流 → setCommandermode(ALTHOLD_MODE)（退化成只定高）
  → stabilizerInit() 读 requiredEstimator，真正启用 kalman 滤波器

  所以"定点模式"能不能生效，取决于开机那一刻光流/测距 deck
  是否被检测到；飞行途中不会因为传感器数据变好或变坏而动态升级/降级模式。

  在这个前提下，起飞/悬停/降落这三个阶段，固件侧做的事其实完全一样——都是同一套串级 PID
  在跟踪地面站/脚本发来的目标位置，区别只是目标值怎么变化：

  - 外环位置 PID（position_controller_pid.c，pidX/pidY kp=1.9 ki=0.1，pidZ kp=1.6 ki=0.5）：只在
    setpoint.mode.x/y/z == modeAbs 时生效，用"目标位置 − kalman 估计位置"算出一个目标速度。
  - 内层速度 PID（pidVX/pidVY kp=25 ki=1.0，pidVZ kp=22 ki=15）：用"目标速度 − kalman 估计速度"算出
    roll/pitch 姿态角和推力。
  - 再往下交给姿态环（controller_pid.c）转成电机指令。

  起飞：地面站/脚本把目标高度从接近 0
  逐渐斜坡抬升到目标值（固件本身没有"自动起飞"这个动作——crtp_commander_high_level.c 里确实编译了
  takeoff()/planner.c 那套自动轨迹规划，但这个项目的定点模式用的是另一条路径，起飞节奏完全由外部持续发送的
  setpoint 决定）。

  悬停：目标位置钉死不变，外环+内层两个 PID 持续把估计位置/速度往目标值上拉。

  降落：目标高度斜坡降到 0；t5/t6 脚本踩出来的经验是——altHoldMode=true 时，固件的 legacy RPYT
  解码器（crtp_commander_rpyt.c）会把 send_setpoint() 的 thrust 参数重新解释成"老式油门摇杆"（>32767
  爬升、<32767
  下降），所以千万不能用推力斜坡去停桨，否则会先命令"爬升"再突然"最大速度下降"，导致落地反弹；同时贴地会有
  6~9cm 的地面效应气垫，Z 位置环压不穿，触地判定要用 range.zrange 原始读数而不是融合后的估计值。

    下洗会让局部气压产生噪声，测距的精度和响应都更好。

  Critical, independently confirmed in planner.c:
  - plan_takeoff() (planner.c:138) refuses unless the planner is IDLE.

  - stop() (plan_stop, planner.c:69-71) sets state to IDLE.

  So calling land() after stop() is not the harmless no-op my design spec claimed
  ("对已经停桨的飞机再发一次 land 命令是已知的、可接受的冗余动作...不会造成新的风险") — it reactivates the
  planner from IDLE into LANDING, and position_controller_pid.c's thrustBase (documented as "should just
  lift the drone") means the motors get near-hover thrust again for ~0.6–1s. This fires on two real paths
  in the script as written:
  - Watchdog aborts mid-hover → stop() cuts power → the with block's __exit__ then calls land() anyway →
    motors re-arm on a drone that may already be down or tipped over.
  - Ctrl+C mid-hover → __exit__ already lands correctly → the outer except fires again and sends a second
    land()+stop() → same re-arm, for a full extra second, right as the operator (per the script's own
    safety instructions) is standing by to catch the drone.

  Important, also confirmed by reading the code:
  - The emergency fallback (land() → sleep → stop()) has no guard — if land() itself raises (e.g. broken
    link, the most likely trigger), stop() never runs and the exception escapes uncaught.
  - The except (KeyboardInterrupt, Exception): block swallows the actual exception and never prints it — on
    a first-ever flight of unverified firmware, that's the most important diagnostic information the
    script could produce.
  - No lock between the watchdog thread and main thread calling cf.high_level_commander — they can
    interleave.

  This is a genuine gap in my own design, not an implementer error — the plan text explicitly mandated the
  "redundant land is harmless" behavior. Given it's a real physical-safety issue on an actual drone, I want
  your sign-off before I dispatch a fix, rather than just patching it silently.

     windup）的典型信号：控制器认为"没到目标高度（0.3m）"，就一直加推力，但实际测出来的高度就是不涨——这通常
     意味着飞机没有保持水平，推力没有转化为垂直升力（倾覆/侧翻/被卡住时最常见）。
  3. yaw 在 300ms 间隔里从 -1.74rad 摆到 +0.38rad（约120°摆幅，折合角速度 >400°/s），远超正常悬停时
     yaw-hold 该有的幅度（起飞前 yaw 只有 0.25-0.27rad，高层命令的目标 yaw 是 0，只需修正约15°）。这种量级
     的摆动不是"估计器漂移"能解释的，更像飞机在物理上打转/侧翻/在地面磕碰弹跳（zrange 0→63→88→36→97…这种非
     单调的忽高忽低，也很像贴着地面弹跳时测距忽而对地、忽而对着倾斜姿态下的空气或障碍物）。
  4. land() 期间 zrange 不降反升（197→235mm），说明此时飞机的真实状态和"降落轨迹"完全脱节——很可能这时飞机已
     经处于失控的翻滚/上扬状态，而不是在按 land() 规划的斜坡下降。PositionHlCommander.land() 是按固定时长（
     height/velocity≈0.6s）阻塞发送轨迹的，跟真实状态没有闭环反馈；这段固定时长跑完之后，脚本紧接着调用
     stop() 立即切断推力（t7 的既有安全设计——不管当时真实姿态/高度如何，land()返回后必定
     stop()）。如果这时飞机因为失控实际处于较高/侧翻的状态，stop()
     一断电就会直接摔下来——这跟你观察到的"最后直接掉下来"是吻合的。

  顺着代码查到的机制

  components/core/crazyflie/modules/src/position_controller_pid.c:225,242-246：
  this.pidVZ.pid.outputLimit = (UINT16_MAX / 2 / thrustScale);
  ...
  *thrust = thrustRaw*thrustScale + this.thrustBase;
  if (*thrust < this.thrustMin) { *thrust = this.thrustMin; }
  这里只做了下限（thrustMin）保护，没有上限保护。
  高度/速度环一旦跟丢目标（不管是真的够不着高度，还是估计器被姿态污染导致误以为高度不够），thrustRaw 会顶到
  outputLimit，算出来的合力 thrust 可以远超 65535（日志里看到的 66767 就是证据——这是 16 位电机 PWM
  的量程上限）。

  components/core/crazyflie/modules/src/power_distribution_stock.c:77,102-105：
  #define limitThrust(VAL) limitUint16(VAL)
  motorPower.m1 = limitThrust(control->thrust - r + p - control->yaw);
  motorPower.m2 = limitThrust(control->thrust - r - p + control->yaw);
  ...
  每个电机是"合力 ± 姿态修正量"算完之后才统一夹到 [0, 65535]。当 control->thrust 本身就已经 ≥ 65535
  时，任何"需要加大某个电机推力"的姿态修正都会被直接吃掉（该电机反正已经封顶），只有"减小某个电机"的修正还
  有效——也就是说一旦总推力打满，姿态环对"需要增推力那一侧"完全失去控制权限,只能单向减推力去纠偏。这跟观测到
  的"持续单向自转 +
  持续单向漂移"（而不是来回抖动）完全吻合：控制器在拼命想修正,但只有半条命,修正不回来,只能眼看着越转越大。

  结论

  - 这不只是"起飞爬升太快"的问题（已经验证：放慢 3.3 倍依然复现）。
  - 是高度/速度环的合力输出没有上限保护，一旦跟丢目标就会把总推力顶穿电机 PWM
    量程，进而在混控环节吃掉姿态修正权限，导致失控自转+漂移，最终"乱飞一洗然后掉地上"。
  - 至于"为什么高度/速度环会跟丢目标"，还有两种可能，需要你帮忙判断：
    - 真实动力不足（螺旋桨/电机磨损、电池电压低、机身变重）——这种情况下就算修好上限保护，飞机大概率也只是"
      推力打满但飞不到 0.3m"，不会失控自转，但也起不来。
    - z 估计被姿态污染——一旦有轻微倾斜，下视测距（zrange）测的不再是真实高度，kalman 估计的 z
      偏低，高度环误以为还没到目标继续加推力，形成恶性循环（哪怕真实动力够）。

  这两种情况都会被"合力无上限保护"这个代码缺口放大成同一种炸机模式，但对应的修复方向不同（前者要降起飞高度/
  检查硬件动力，后者是估计器/控制器的问题，光调 Python 参数解决不了）。
