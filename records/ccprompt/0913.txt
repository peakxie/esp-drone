这个 bug 到底是怎么回事 

  这实际上是两个独立问题叠加,缺一不可才会造成"提前降落"这类事故:

  问题1:z 轴根本没有前馈,是纯反馈闭环

  position_controller_pid.c:218-219:
  if (setpoint->mode.z == modeAbs) {
      setpoint->velocity.z = runPid(state->position.z, &this.pidZ, setpoint->position.z, DT);
  }
  这一行是覆盖而不是叠加——planner 算出来的
  ev.vel.z(轨迹在当前时刻"应该"有多快)被直接丢弃,唯一起作用的是当前高度 vs 目标高度这一个位置误差过的
  P(I)D。正确的轨迹跟踪架构应该是 feedforward + feedback(ev.vel.z + runPid(...)),现在这里只有 feedback。

  后果:如果 planner 给的是一条很平滑、很慢的爬升斜坡(比如 3.5s 爬到
  0.3m),那么在斜坡的每一时刻,"目标位置"本身移动得很慢,离飞机当前实际位置就很近——位置误差因此一直很小,PID
  算出来的速度指令/推力修正也一直很小,飞机实际上几乎不动。真实证据来自 t7_hl_commander_check.py
  里记录的第四次实机测试:把爬升时间从 2.0s 拉长到 3.5s(想让爬升更"温柔"),结果整个 3.5s 窗口里 zrange
  完全没离开地面噪声——直到 take_off() 返回、目标高度不再前移、固定死在终点,误差才终于攒够大小,PID
  才真正发力爬升。也就是说:轨迹越平滑/越"安全",z 轴实际动得越少,这跟直觉正好相反,根源就是这个丢前馈的 bug。

  问题2:"完成"信号是纯时钟,不看物理状态

  无论是固件 planner 的 plan_is_finished(t),还是 Python 侧 land()/take_off() 内部的

  Architecture: new components/core/crazyflie/modules/{src,interface}/sequencer.c/.h, a dedicated FreeRTOS
  task (~20ms cadence, matching the VL53L1 driver's own 25ms update rate) that owns the step state machine
  and publishes a mutex-protected setpoint. crtp_commander_high_level.c gets new opcodes in its existing
  enum TrajectoryCommand_e dispatching into sequencer.c, and
  crtpCommanderHighLevelGetSetpoint()/crtpCommanderHighLevelIsStopped() get a small hook to check "is the
  sequencer active" first. Old takeoff2/land2/goto/planner.c code path is untouched.

  Wire protocol (same CRTP port, CRTP_MAX_DATA_SIZE=30): SEQ_CLEAR(11)/SEQ_ADD_STEP(12, uint8_t type +
  float[7], exactly 30 bytes)/SEQ_START(13)/SEQ_CANCEL(14, new); STOP(existing opcode 3) reused for e-stop.
  Step types: 0=TAKEOFF_SENSOR(target_m, stable_hold_s, timeout_s), 1=DELAY(hold_time_s), 2=LAND(target_m,
  duration_s), 3=GOTO_SENSOR reserved/rejected this round. Max 16 steps.

  State machine: IDLE → RUNNING → (LANDING) → IDLE. TAKEOFF_SENSOR ramps z at a tunable fixed velocity,
  completes on stable_hold_s continuous tolerance-match against raw range.zrange, aborts to LANDING on
  timeout_s (your confirmed policy — same code path as CANCEL). DELAY just holds and waits out hold_time_s.
  LAND ramps over duration_s, confirms touchdown via raw range.zrange threshold + confirm-time, hard-caps
  the wait, then cuts motors. STOP reused opcode → both old planner and sequencer report idle → commander.c
  nulls the setpoint immediately (true e-stop, no ramp). START requires the last uploaded step to be LAND
  and the old planner idle.

  Tunables (PARAM_GROUP_START(seq), defaults borrowed from already-flight-tuned Python values): takeoff
  ramp velocity, takeoff tolerance, touchdown threshold + confirm time, land max-wait, cancel-land
  duration, sane-range ceiling (4000mm).

  Telemetry (LOG_GROUP_START(seq)): state, step index, step type, elapsed-in-step — enough for a Python
  script to watch progress without driving it.

  mode.y=modeAbs, position.y=0, mode.yaw=modeAbs, attitude.yaw=0, continuously, from SEQ_START through

  rotated off yaw=0, the PID commands roll/pitch/yaw corrections to steer back, exactly like an ordinary
  hover-hold.

  The catch is what "the estimate says":
  - Yaw: pure gyro integration (no magnetometer, per the earlier discussion). Over a few-second sequence
    with no deliberate rotation, gyro drift is negligible — so yes, yaw-hold-at-0 is trustworthy here: if
    something nudges the drone's heading, the correction is real and based on a real (if not
    absolutely-referenced) measurement.
  - x/y: only meaningfully closed-loop if you have a flow deck (PMW3901, flowdeck_v1v2.c) feeding the
    Kalman estimator with real optical-flow velocity measurements. t7_hl_commander_check.py already checks
    for this (stabilizer.estimator == 2 = kalman) and prints a warning otherwise: "没有检测到光流
    deck...没有水平位置修正时飞机可能会缓慢漂移". Without a flow deck, state->position.x/y is just
    double-integrated accelerometer noise — it doesn't represent where the drone actually is, so the PID is
    "closed loop" against a fiction: if the drone physically drifts, the estimate won't necessarily
    reflect it, and the controller won't correct it. The loop is real, but only as good as what it's
    measuring against.

  estimator check t7/t6 already do in the new t8 script (warn if not kalman, don't block) rather than
