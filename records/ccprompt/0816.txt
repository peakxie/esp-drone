 启用 pyDrone 板载 PMW3901 + VL53L1X（Flow Deck 功能）

 Context

 之前的迁移工作（见 records/espdrone.md、commit 212e98d）把 pyDrone 硬件适配进了 esp-drone，
 当时结论是 pyDrone 没有扩展板、SPI 引脚被 Octal PSRAM（GPIO35/36/37）占用，所以把
 CONFIG_SENSORS_ENABLE_DECK（对应 SENSORS_ENABLE_RANGE_VL53L1X + SENSORS_ENABLE_FLOW_PMW3901
 两个条件编译宏，components/core/crazyflie/hal/src/sensors_mpu6050_hm5883L_ms5611.c:92-96）默认关闭，
 ENABLE_POSITION_HOLD_MODE 默认关闭，只能自稳飞行。

 现在硬件已经改板，实际焊上了 PMW3901（光流）+ VL53L1X（ToF 测距），走的是：
 - I2C1（deck 总线）：SCL=GPIO1，SDA=GPIO6 —— 与当前 TARGET_PYDRONE_S3 的 I2C1_PIN_SCL/SDA 
   默认值完全一致，无需改动
 - 独立 SPI：MISO=GPIO17，MOSI=GPIO21，CLK=GPIO18，CS=GPIO8 —— 这组脚不与 Octal PSRAM 占用的 35/36/37/34
   冲突，
   也不与已用的电机(4/5/40/41)、LED(46/42)、I2C0(15/16)、MPU_INT(7)、ADC(2) 冲突

 驱动层代码（zranger2.c 用 I2C1_DEV，flowdeck_v1v2.c/pmw3901.c 用 CONFIG_SPI_PIN_CS0 做 CS，SPI 总线脚
 纯读 Kconfig）已经是通用实现，不需要改一行 C 代码——CMakeLists 里 deck/pmw3901/vl53l1 组件对所有板型
 都无条件参与编译（components/core/crazyflie/CMakeLists.txt:72），运行时行为完全由 Kconfig
 决定。所以这次纯粹是
 Kconfig 引脚 + 默认值调整，把"新增的 3 个条件"（SENSORS_ENABLE_MAG / SENSORS_ENABLE_PRESSURE /
 SENSORS_ENABLE_DECK）里的 SENSORS_ENABLE_DECK 从关闭改为打开，并把 SPI 默认脚从占用 PSRAM 的 35/36/37/34
 改成板子实际走线的 17/21/18/8。

● 对，是两条独立的 SPI 硬件总线，互不共享：

  - PSRAM（Octal PSRAM）：由 ESP32-S3 内部专用的 SPI 控制器驱动（CONFIG_SPIRAM_MODE_OCT），占用
    GPIO35/36/37 等一组专用引脚，完全由 ESP-IDF 的 SPIRAM 驱动接管，用户代码碰不到、也不需要碰。
  - PMW3901：走的是通用 SPI 外设 SPI2_HOST（components/drivers/deck/deck_spi.c:77），用
    CONFIG_SPI_PIN_MISO/MOSI/CLK/CS0（现在是 17/21/18/8）这组独立引脚，由 spiBegin() 在运行时初始化，跟
    PSRAM 那条线完全是两个硬件控制器，物理上和逻辑上都不冲突。

  所以这次改动本质上就是给 PMW3901 挂到 SPI2_HOST 这条"第二条 SPI"上，PSRAM
  那条留给内部固定用途，两者各自独立工作。

基于代码里实际的 param/log 组名和连接方式，把 T1-T7 逐条落到可执行的操作上：

  准备

  - 拆桨（螺旋桨从电机上取下，只留电机空转）。
  - 手机连不上就用 PC + cfclient：git clone https://github.com/qljz1993/crazyflie-clients-python.git &&
    pip3 install -e . && cfclient
  - ESP-Drone 上电后会开 AP：SSID ESP-DRONE_XXXX（XXXX 是 MAC 后四位），密码 12345678
  - cfclient 里 Connect 地址填：udp://192.168.43.42:2390
  - 串口日志（USB-Serial-JTAG，/dev/ttyACM0）全程开着：idf.py -p /dev/ttyACM0 monitor

  T1 — 上电不转桨

  1. 螺旋桨全部取下，接电池。
  2. 盯着串口日志，不要有 i2c driver install 相关报错。
  3. 目测/用手轻触 M3、M4 对应电机轴（GPIO40/41 现在应该只是普通电机脚），上电瞬间不应该抽动或转动。
  4. 通过：日志无 I2C 报错 + M3/M4 电机静止 → 证明 deck I2C 已经改到了 GPIO1/6，没有误配到电机脚上。

  T2 — I2C/SPI 扫描

  1. 只看串口日志里初始化阶段打印的这几行（DEBUG_MODULE "SENSORS"）：
     - MPU6050 I2C connection [OK]
     - SPL06 I2C connection [OK]
     - VL53L1X I2C connection [OK] ← 这次新加的，没出现就说明 I2C1(GPIO1/6)接线或时序有问题
     - PMW3901 SPI connection [OK] ← 这次新加的，没出现就查 SPI(GPIO17/21/18/8) 接线，尤其 CS(GPIO8)
  2. 连上 cfclient 后打开 Parameter 面板，展开 imu_tests 组，读取：
     - imu_tests.mpu6050 应为 1
     - imu_tests.pmw3901 应为 1（对应 flowdeck2Test() 通过）
     - VL53L1X 目前代码里没有单独的 param 标志（只有串口日志），所以它的"在线"判断要看第 3 步的 log
       数值，不是 param。
  3. 打开 Log 面板，订阅 range.zrange：静止时应该有一个稳定的非 0/非 0xFFFF 数值（单位 mm），说明 VL53L1X
     真的在回数据，不只是初始化成功。

  T3 — 电机映射 + 方向（这一步最危险，务必确认桨已拆）

  1. cfclient Parameter 面板，motorPowerSet 组：先设 motorPowerSet.enable =
     1（这会绕开飞控直接给单个电机赋值）。
  2. 依次只给一个电机赋值（比如 motorPowerSet.m1 = 10000，其余 m2/m3/m4 保持
     0），观察哪个电机转，确认物理位置：
     - 按文档结论应为 M1 左上、M2 右上、M3 右下、M4 左下（若实际不一致，要去改 MOTOR01_PIN..MOTOR04_PIN
       或接线，而不是软改序号语义）。
  3. 每测完一个立刻把该 m 设回 0，再测下一个，最后 motorPowerSet.enable = 0 交还给飞控。
  4. Pitch 符号判定：把 4 个电机都设一个小的低速值，手动模拟推杆抬头（想象机头方向），对照
     power_distribution_stock.c 里 CONFIG_PITCH_DISTRIBUTION_INVERTED 关闭/打开两种情况下 m1-m4
     的公式，判断哪一组符合"机头抬起时前两个电机减速、后两个加速"（或反之，取决于机头朝向定义）。若现在默认
     （未反转）验证是错的，就在 idf.py menuconfig 里打开 Power distribution -> Invert the pitch
     term，重新走一次 T3。

  T4 — 传感器读数

  1. cfclient Log
     面板订阅：acc.x/y/z、gyro.x/y/z、mag.x/y/z、baro.asl、range.zrange、motion.deltaX/deltaY。
  2. 静置在水平桌面：
     - acc.z ≈ 1.0（g），acc.x/y ≈ 0（有偏差用 PITCH_CALIB/ROLL_CALIB 校正，单位 deg*100）
     - gyro.x/y/z ≈ 0，绕某轴手动转动飞机，对应轴数值应按右手定则变化
     - 抬升飞机高度，baro.asl 应单调增大；用手掌在飞机下方由远到近移动，range.zrange 应单调减小到几十 mm
       量级
     - 手托着飞机平移，motion.deltaX/deltaY
       应有非零脉冲，方向要和平移方向对应（不对的话是光流安装朝向问题，代码里 flowdeck_v1v2.c 已经做了
       -deltaY/-deltaX 翻转，如果反了要重新核对贴装方向再决定是否再加一次翻转）

  T5 — 电池电压

  1. cfclient Log 订阅 pm.vbat（或 pm.vbatMV）。
  2. 万用表实测电池正负极电压，与 pm.vbat 对比，误差应 < 0.1V。
  3. 超差说明 BAT_DIVIDER_RATIO=502 或 BAT_ADC_ATTEN_0DB 这两个 Kconfig

  1. cfclient 用上面的 udp://192.168.43.42:2390 连接，确认状态变绿、Parameter/Log 树能正常展开读取（做完

  T7 — 系留悬停

  1. 用绳子/胶带把飞机系在稳定支架上，留出足够行程但不能真正飞脱。
  2. 装回螺旋桨，小油门起飞到系留绳张力附近，观察是否发散（自振/持续漂移）。
  3. 因为这次 ENABLE_POSITION_HOLD_MODE=y 已经打开，光流+ToF 都在线的情况下，用 cfclient

  4. 系留稳定后才考虑解开绳子自由试飞。

  硬件层面（取决于板子供电拓扑，我在仓库里查不到这块自定义板/扩展硬件的原始图，不能替你下结论）

  有刷电机电路的典型接法是：GPIO(LEDC PWM) 只驱动一个低边 N-MOS
  管的栅极，电机另一端接的是系统/电池供电轨（VBAT），不是 3.3V 逻辑电。也就是说桨会不会转，最终取决于 VBAT
  这条轨有没有电：

  - 如果板子设计是"USB 只经过一个独立的 5V→3.3V LDO 给 MCU 供电，跟 VBAT 完全不搭",那只接
    USB、不接电池时，电机那端根本没有电压源，GPIO 怎么开关 MOS
    管都没用——这种情况下是硬件级保护，跟软件无关。
  - 但如果板子上有电源管理/充电芯片（文档里提到过黄色 LED 是充电 STAT 脚，说明板上确实有一颗类似 TP4056
    的芯片），而这颗芯片的系统输出轨在"只接 USB 不接电池"时依然会把
    VBAT/系统轨拉起来（很多板子这么设计，方便台架调试不用挂电池）——那这种情况下电机supply
    就是带电的，唯一的保护就是软件。

  这一点我没法只看固件代码确定，建议你实测一下：只插 USB、不接电池，用万用表量任意一个电机负极那颗 N-MOS
  的漏极（或者直接量 VBAT 测试点）对地电压——读到 ~0V 说明是硬件保护，读到接近电池电压说明是软件在兜底。

  软件层面（这个是确定的，而且是个新发现）

  我查到 components/drivers/general/motors/motors.c:157 的 motorsTest()：只要 VBAT
  有电，固件在每次开机自检时，会按 M1→M2→M3→M4 顺序依次让每个电机以 20% 油门转 50ms、间隔 150ms——这是
  stabilizerTest() → powerDistributionTest() → motorsTest()
  这条自检链路里硬编码的行为（components/config/include/config.h:196 里 ACTIVATE_STARTUP_SOUND
  默认是关的，所以走的是真实转一下而不是蜂鸣器哔一声这个分支）。

  结论：这不是"万一软件出 bug 才会转"，而是"只要 VBAT 有电，每次开机固件本来就设计成会依次转一下 4
  个电机"。 所以：
  - 如果你的板子 USB-only 时 VBAT 是真的没电（硬件保护），那插 USB 看日志/调 Kconfig 是绝对安全的。
  - 如果 VBAT 在 USB-only
    时也带电，那这个自检序列每次开机都会跑一遍——即便你什么命令都没发，桨也会短暂转一下，这时候拆桨做 T1/T2
    就不是"谨慎起见"，而是必须，因为这个动作是确定会发生的，不是假设性风险。

● 这是配置问题，不是代码 bug。

  原因：xQueueHandle / xSemaphoreHandle 这些是 FreeRTOS 的旧式类型名，只有在开启
  configENABLE_BACKWARD_COMPATIBILITY 时才会存在（新版本已改名为 QueueHandle_t 等）。这个仓库的
  sdkconfig.defaults:13 已经正确写了：

  CONFIG_FREERTOS_ENABLE_BACKWARD_COMPATIBILITY=y

  但 sdkconfig.defaults 只在第一次生成 sdkconfig 时生效，如果你本地已经有一个之前生成的 sdkconfig（比如换过
  IDF 版本、换过 target、或者是老项目残留的），里面没有这一项，新加的默认值就不会自动补进去，于是 FreeRTOS
  编译时就没启用兼容层，导致 xQueueHandle 未定义。

  解决方法（任选一种）：

  1. 删掉旧的 sdkconfig（不是 sdkconfig.defaults，那个别删），重新配置：
  rm sdkconfig
  idf.py set-target <你的target>   # 如 esp32s2 / esp32s3
  idf.py build
     这样会重新按 sdkconfig.defaults 生成。
  2. 或者不删，直接跑 idf.py menuconfig，进入：
     Component config → FreeRTOS → Kernel → 勾选 Enable FreeRTOS backward compatibility
     保存退出后再 idf.py build。

  推荐用第 1 种，避免和其他手动改过的 sdkconfig 选项混在一起排查更麻烦。

● sdkconfig.defaults.pydrone 是叠加在通用配置之上的板级增量配置，两者是分层叠加关系，不是互相替代：

  - sdkconfig.defaults：所有硬件目标共用的基础配置（FreeRTOS 参数、编译优化选项、WiFi
    发射功率等），跟具体是哪块板子无关。
  - sdkconfig.defaults.pydrone：只包含 01Studio pyDrone v1.0（ESP32-S3-WROOM-1
    N8R8）这块板子特有、需要覆盖/追加的选项，比如 CONFIG_TARGET_PYDRONE_S3=y、8MB flash、Octal PSRAM
    配置、走 USB-Serial-JTAG 控制台而不是 UART 等。

  文件开头的注释里已经写明了用法（sdkconfig.defaults.pydrone:1-8）：

  idf.py set-target esp32s3
  idf.py -D SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.defaults.esp32s3;sdkconfig.defaults.pydrone"
  reconfigure

  即通过 SDKCONFIG_DEFAULTS 传一个用分号分隔的列表，idf.py 会按顺序依次应用这几个文件（sdkconfig.defaults →
  sdkconfig.defaults.esp32s2/esp32s3 → 板级文件），后面的文件里的选项会覆盖前面的。这样通用配置只写一份，
  各板子只需维护自己的差异部分，不用每块板子都复制一份完整 sdkconfig.defaults。

  另外注释里也提到更简单的方式：在 idf.py menuconfig → ESPDrone Config 里直接选 "01Studio pyDrone with
  ESP32-S3 onboard"，Kconfig 会自动帮你选中对应 TARGET，效果上等价于手动叠加这些 defaults
  文件（前提是这个选择逻辑在 main/Kconfig.projbuild 里做了对应的 default 联动）。

  如果你是要给 pyDrone 板子编译，记得用上面那条带 -D SDKCONFIG_DEFAULTS=... 的命令，而不是只跑 idf.py
  build——否则不会应用 sdkconfig.defaults.pydrone
  里的配置，这也是导致之前编译/配置项缺失问题的常见原因之一。

  1. 电机个体差异（最常见）：这是有刷空心杯电机，同批次电机的摩擦力、电刷磨损、绕组阻值都会有个体差异，尤其
     是没装桨空转时，负载很小，这种差异会被放大——转得快/响不代表这个电机"更好"，也可能是磨损更松、内阻更低

  3. 机械问题（如果"响"指噪音而不是转速）：电机没装正、和机架有轻微摩擦、轴承有杂音，这种"响"是噪声而不是真

● 这个数据不太干净,先解释一下——我觉得测试方法本身有个设计缺陷,不是电机坏了或者符号错了。

  m4=0、m2 持续增大是怎么回事

  M2 和 M4 在你的机架上是对角线(M2=右下,M4=左上)。公式里它俩的 roll、pitch 符号刚好相反:
  m2 = thrust - r - p - yaw
  m4 = thrust + r + p - yaw
  如果 r+p 这个合成偏置一直往一个方向走,会表现成"m2 一直涨、m4 一直被顶到 0(被 limitThrust
  钳到下限)"——跟你观察到的现象完全对应。所以这不是 M4 单独坏了,是姿态环积分项在持续跑飞。

  为什么会跑飞——测试方法的问题

  没装桨的情况下,电机转动不会产生真实的空气动力矩,姿态估计感受不到任何"纠正生效"的反馈。但姿态 PID
  的积分项(I)是假设"输出会让误差变小"设计的——在台架上这个假设从物理上就是错的,只要存在一丁点姿态零偏(传感器
  没校准到绝对零、桌面不是绝对水平),积分项就会无止境地越攒越大,而且完全不会收敛。我这个脚本让闭环持续跑几十

● MPU6050 与机身坐标系的关系

  processAccGyroMeasurements()（components/core/crazyflie/hal/src/sensors_mpu6050_hm5883L_ms5611.c:423-483
  ）中，非 ESPLANE_V1（即 pydrone-s3 用的分支，见 sdkconfig.defaults.pydrone:10 
  CONFIG_TARGET_PYDRONE_S3=y）分支做了这件事：

  accelRaw.y = ...buffer[0..1]   // MPU6050 ACCEL_XOUT 寄存器
  accelRaw.x = ...buffer[2..3]   // MPU6050 ACCEL_YOUT 寄存器
  accelRaw.z = ...buffer[4..5]   // MPU6050 ACCEL_ZOUT 寄存器
  ...
  accScaled.x = -(accelRaw.x) * G_PER_LSB / accScale   // = -mpu.Y
  accScaled.y =  (accelRaw.y) * G_PER_LSB / accScale   // = +mpu.X
  accScaled.z =  (accelRaw.z) * G_PER_LSB / accScale   // = +mpu.Z

  即：

  - 机身 X（前）= −芯片 Y
  - 机身 Y（左）= +芯片 X
  - 机身 Z（上）= +芯片 Z

  换算成旋转关系：芯片相对机身绕 Z 轴转了 +90°（芯片 X 轴实际指向机身左侧，芯片 Y 轴指向机身后方，Z
  轴与机身 Z 轴重合、都朝上）。这正是代码注释 "Note the ordering to correct the rotated 90º IMU coordinate
  system" 所说的——MPU6050 芯片在 PCB 上物理贴装方向和机身前向差 90°，固件在这里把它转回机身坐标系。

● 调研完成，关键结论如下:

  可能原因

  30000/65535 ≈ 46%油门，这个值本身在合法范围内，不是参数越界问题（motors.h里PWM是16位参数，转换成8位LEDC
  duty时右移8位，30000→duty
  117/255）。真正可疑的是"持续一段时间后重启"这个现象，结合代码看，最可能是硬件Brownout复位：

  - t3_motor_mapping.py 里设置电机后会阻塞在 input()
    等你按回车，也就是电机会以固定duty持续转很长时间（不是脉冲测试）。
  - 该脚本走的是 motorPowerSet.enable=1 直接写 power_distribution_stock.c 里的
    motorPowerSet.m1~m4，完全绕过了commander/stabilizer，所以commander的通信超时保护根本不会触发（它也从来
    不会导致MCU重启，只会把setpoint清零）。
  - 全仓库搜不到任何 brownout 相关配置，说明ESP-IDF的默认硬件brownout检测（约2.43V
    VDD33阈值）是启用状态，没有被关闭或调低。
  - 固件里没有真正的过流/欠压软件保护——pmSystemShutdown() 是空的TODO实现，ACTIVATE_AUTO_SHUTDOWN
    没定义，所以电池电压跌落时软件不会主动降功率或保护性关闭。

  也就是说：单个/多个电机在46%油门下持续转动，电流拉高导致电池/3.3V共用电源轨电压跌落，触发ESP32自带的brown
  out detector把芯片复位——这和"设置30000一会儿后系统重启"的现象高度吻合。

  次要可能性：代码中若某个ASSERT()触发，会进入 cfassert.c 里 portDISABLE_INTERRUPTS(); while(1); 的死循环，
  进而被任务/中断看门狗判定为卡死强制复位芯片，但目前没找到该路径被触发的直接证据，优先级低于brownout。

  如何进一步验证

  1. 直接读取复位原因（最关键、最直接的证据）：在固件里加一行调用 esp_reset_reason()（ESP-IDF
     API）并通过UART/CDC log打印出来，或看是否已有代码打印。复位后串口应输出类似
     RTCWDT_BROWN_OUT_RESET（brownout）或
     TG0WDT_SYS_RESET/RTC_SW_CPU_RESET（看门狗/assert死循环）。这一步能直接区分两种猜测，不需要猜。
  2. 测电压：设置30000让电机持续转动时，用万用表或示波器实测电池电压和3.3V
     rail，看是否在重启瞬间跌到~2.4~2.5V附近（brownout阈值区间）。如果确认，就是电源/brownout问题。
  3. 梯度测试定位阈值：把 TEST_VALUE
     从10000开始按步长（15000/20000/25000/30000...）测试，记录每个值能持续转多久不重启，看是否存在明显的电
     流/占空比阈值——如果阈值一致地对应某个电压跌落点，进一步坐实brownout假设。
  4. 换电源排除电池因素：用稳压实验室电源（带足够电流余量）替代电池供电做同样测试，如果换电源后不再重启，说
     明是电池内阻/电量不足导致的电压跌落，而非固件逻辑bug。
  5. 检查串口log是否在重启前打印过ASSERT相关信息，排查/确认是否是assert死循环+看门狗路径。
  6. 如果确认是brownout触发，后续修复方向是：在sdkconfig里调整/关闭brownout阈值（需谨慎，brownout本身是保护
     机制）、改善供电（加大电容、独立供电电机与MCU）、或者补上pmSystemShutdown()的软件低压保护逻辑，在电压
     跌落前主动限制电机输出而不是让硬件强制复位。

● 可以缓解，但效果有限，取决于掉压的具体原因和电容的位置/类型。

  电容能解决的部分：
  - 电池内阻（ESR）在电机启动/PWM高频通断时会产生瞬态电压尖峰/跌落。在电池到主控/传感器供电入口处并联低ESR
    电容（钽电容、固态电容，甚至陶瓷电容+电解电容组合），可以就近补充瞬态电流，减小这类高频毛刺。
  - 如果掉压表现为MCU复位、传感器读数抖动、Wi-Fi/无线模块重启，通常就是这类高频噪声耦合到逻辑电源轨，加电容
    （尤其在MCU/IMU供电入口，而不是电池两端）见效更快。

  电容解决不了的部分：
  - 如果是电池老化、内阻本身过大，或C-rating不够，在大电流持续拉载（如爬升、翻滚）时电压持续下降数百毫秒以
    上——这种"能量不够"的持续掉压，普通电容储能太小（几百µF/几十mF
    撑不了这种能量需求），基本没用，除非上超级电容（法拉级），但esp-drone这种小机重量/体积很难塞下。
  - 电池两端并联只是"离电源近"，但如果电机走线/连接器本身电阻大（接触不良、线径细），压降发生在电池到电机之
    间的路径上，电容加在电池两端也救不了负载端的压降。

  建议顺序：
  1. 先确认掉压是瞬态噪声还是持续性下降（用示波器看波形，区分成因）。
  2. 检查电池内阻/健康度、连接器接触电阻、走线线径——这些往往是根因。
  3. 若是逻辑电源轨受电机电流干扰，优先做电源分域（MCU/传感器独立稳压+就近去耦），而不是在电池两端堆大电容
     。
  4. 电容选型上，低ESR的钽/固态电容效果远好于普通铝电解，位置尽量靠近受影响的负载（MCU/IMU），而不是电池端
     子本身。
