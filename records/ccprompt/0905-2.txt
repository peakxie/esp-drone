找到了，而且是个明确的根因，不是猜测——问题出在我们自己加的 ramp_down_thrust() 上，跟地面效应没关系。

  证据链：

  1. 固件里 sensors_mpu6050_hm5883L_ms5611.c:635 检测到光流/测距 deck 在线时会自动调用
     setCommandermode(POSHOLD_MODE)（脚本注释里提过这件事）。
  2. 这个函数（crtp_commander_rpyt.c）把两个全局标志 altHoldMode 和 posHoldMode 都置为 true——每次飞行日志里
     stabilizer.estimator=2(kalman) 都证实了这条分支被走到了。
  3. 关键：altHoldMode/posHoldMode 这两个标志只影响 legacy RPYT 解码器（也就是 cf.commander.send_setpoint()
     走的那个通道，send_position_setpoint 走的是另一个通道，不受影响）。看 crtp_commander_rpyt.c
     里的解码逻辑：

  if (altHoldMode) {
      setpoint->mode.z = modeVelocity;
      setpoint->velocity.z = ((float) rawThrust - 32767.f) / 32767.f;   // 不是原始推力！
  } else {
      setpoint->mode.z = modeDisable;   // 只有这条分支才是"原始推力直通"
  }

  也就是说，一旦 posHoldMode 生效（这个项目每次真实飞行都会生效），send_setpoint() 的 thrust
  参数就不再是"原始推力"了，而是被重新解读成一个老式"油门摇杆"信号：thrust=32767 是"悬停不动"，thrust>32767
  是"爬升"，thrust<32767 才是"下降"，而且是线性映射到 ±1m/s。

  我们的 ramp_down_thrust() 从 ~50000 斜坡降到 0——按这个公式算：
  - 50000 → +0.53 m/s 爬升
  - 32767 → 0（悬停）
  - 0 → -1.0 m/s 下降

  这正好完整解释了你说的"落地了、又弹起、再重重摔下去"：斜坡前半段（thrust 还在 32767 以上）其实是在命令飞
  机往上爬，跟地面效应完全无关，是我们自己这段代码把"降推力"误当成了"降油门摇杆"在发；等 thrust 降到 32767
  以下，命令又突然变成最大 1m/s 的下降速度，直冲下去，摔得比原来的硬停桨还狠。日志里
  thrust=66767（这个数正好等于 Z 速度环最大输出上限32767 + thrustBase
  34000）也对得上——那是飞机拼命响应"爬升"指令、速度环打满饱和的痕迹。

  结论：ramp_down_thrust() 这个我加的"平滑推力斜坡"从一开始就是错的，一直在制造这个弹跳，不是地面效应。

  0~10mm），这时候直接硬停桨，落差不到1cm，根本不需要什么斜坡。

  我建议：去掉 ramp_down_thrust()，触地确认后直接调 send_stop_setpoint()（回到最早的做法），可以吗？
