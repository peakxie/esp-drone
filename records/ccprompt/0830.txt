  e16b36c，8-26）绕开的，但代码本身没改——一旦以后重新启用光流模块，这个"静默劫持摇杆"的行为会立刻复现。

❯ m1m3的顺时针旋转，现在固件中yaw对吗？

把 yaw 这条链路从"陀螺仪→双闭环 PID→混控→电机"完整过一遍符号，用你给的 M1/M3
  顺时针（俯视）这个事实来对，结论是：现在的固件里，yaw 大概率是反的——跟当年 pitch 的 bug
  是同一类问题，只是藏在另一处。

  推导过程

  1. 陀螺仪 Z 轴没有做任何取反（sensors_mpu6050_hm5883L_ms5611.c:467）：
  sensorData.gyro.z = (gyroRaw.z - gyroBias.z) * SENSORS_DEG_PER_LSB_CFG;  // 不取负
  你只提到 X/Y 轴的换轴/取负，没提 Z 轴要翻转，说明芯片 Z 轴跟机身 Z
  轴（朝上）是同向贴装的。芯片自身的"陀螺 Z 轴正转"按右手定则，等于从上往下看是逆时针(CCW)——这是几乎所有
  MEMS 陀螺（包括 MPU6050）datasheet 里统一的定义。所以：gyro.z 正值 = 机身俯视
  CCW，且姿态融合、attitudeDesired.yaw 全程都在用同一个约定，没有第二次反转（这点 08-27
  号已经逐项核对过，yaw 跟 roll 一样没被单独处理，只有 pitch 被反过）。

  2. 角速度环 PID 是标准 error = desired - measured（pid.c:62），kp>0：也就是"当前 CCW 转速不够、还想要更多
  CCW"时，pidYawRate 原始输出是正的。

  3. 但 controller_pid.c:116 紧接着把它取反了：
  attitudeControllerGetActuatorOutput(&control->roll, &control->pitch, &control->yaw);
  control->yaw = -control->yaw;   // <-- 这一行
  这行代码是初次移植（2020-05）就带进来的原始代码，从未因为这块板子的实际转向被重新验证过——t4c_rpy_step_res
  ponse_check.py 里 yaw 那两条 "expect" 字符串，注释写的是"来自 power_distribution_stock.c
  的混控公式"，也就是直接从代码反推出来的，跟当年 pitch
  踩过的坑一模一样：拿代码自己的假设去验证代码自己，不是独立证据。

  4. 混控（power_distribution_stock.c:98-101）：m1 += control->yaw，m3 += control->yaw，m2 -=
  control->yaw，m4 -= control->yaw。

  串起来：想要更多 CCW → 角速度环原始输出为正 → 第 116 行取反变成负 → control->yaw 为负 → m1、m3（你确认的
  顺时针电机）转速反而降低，m2、m4（逆时针电机）转速升高。而顺时针电机转速降低=减少它们带来的 CCW 反作用力
  矩，逆时针电机转速升高=增加它们带来的顺时针反作用力矩——两者叠加，合力矩净变化是更顺时针，跟"想要更多
  CCW"完全反着来。

  这不是"方向定义反了但收敛"那种温和问题，而是角速度内环本身的负反馈变成了正反馈：偏差越大、修正动作越往错
  误方向推，跟当年 CONFIG_PITCH_DISTRIBUTION_INVERTED=y 时 pitch 的表现是同一种病。

  需要你确认的唯一前提

  这个结论建立在"MPU6050 是正面朝上贴装、Z 轴跟机身 Z 轴同向"这一条上（因为代码对 Z
  轴没做任何取负处理）。如果芯片其实是倒装（背面朝上）的，结论会反过来。这一点你之前只描述了 X/Y
  的贴装关系，Z 轴需要你确认一下。

  不要相信 t4c_rpy_step_response_check.py 里 yaw 那两条 "expect" 文字，按 t4b 那次揪出 pitch bug
  的方法重新跑一遍：桨叶拆除、机身固定夹死，发一个持续的 yaw 阶跃（比如改用 t4b_pitch_response_check.py
  的模式，或者手动扭转机头看 motor.m1~m4 +

  controller_pid.c:116 的 control->yaw = -control->yaw（比等效地改混控矩阵符号更集中、影响面更小，因为
